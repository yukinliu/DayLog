# DayLog Desktop 开发计划

> 最后更新：2026-08-12
> 版本：v0.2.0
> 适用范围：`daylog-desktop` macOS 本地桌面版
> 状态：MVP 实施基线

## 一、当前判断

开发调试统一从项目根目录运行 `npm run tauri:dev`。不要直接运行
`src-tauri/target/debug/daylog-desktop`：它可能是开发模式二进制，脱离
Vite 开发服务器后只会显示空白窗口。需要独立运行时，使用
`npm run tauri:build` 生成包含前端资源的 `.app`。

DayLog Desktop 已完成主要页面和 Tauri 桌面壳，当前阶段不是继续增加页面，而是把静态测试数据原型收敛为可长期使用的本地产品。

已经具备：

- Tauri 2 + Vite + React + TypeScript 工程。
- 记录、明细、项目、统计、日历、关照和设置界面。
- 基础数据类型、校验、Markdown 生成逻辑。
- 项目合并、删除、状态与统计交互原型。
- macOS `.app` 历史构建产物。

2026-08-10 已完成第一轮本地资料库接入：

- 正式启动不再加载测试数据。
- 已接通新建、打开、记住和更换资料库。
- 文件操作收进 Rust，前端不再拥有整个主目录读写权限。
- 保存进入单一队列，并使用同目录临时文件替换。
- 每次操作只写相关 JSON 和受影响日期 Markdown。
- 删除某日最后一条记录时删除对应 Markdown。
- 已增加保存中、短暂的“已保存到本地”、保存失败和重试状态。
- 关闭与更换资料库前会等待保存，并保护记录页会话草稿。
- 明细、统计和项目页采用一页工作区，长内容在所属区域内部滚动。
- 日历按日展示投入前三的已命名项目，其余内容使用中性色汇总。
- 项目使用后台稳定分配的敦煌 12 色：优先未使用色，其次已结束项目释放色，最后才复用最少使用色；设置页不展示内部配色色板。
- 项目名称和想法不再逐字写盘。
- 明细页已收拢为“内在记录 / 外在经历”两区，事件详情采用 800 毫秒防抖自动保存。
- 统计和明细时间圆环同时显示扇区百分比，统计页将时间分布置于较宽的左侧区域。
- 顶部栏改为居中的 `刘迷糊 DayLog · 见己`，不再重复功能页名称，并压缩高度释放页面空间。
- 产品名移入 macOS 原生标题栏所在空间，彻底取消页面内品牌栏；明细页移除明显中轴线，项目状态改为统一分段控件，统计页固定四项完成状态并整体垂直居中。
- 统计页字号收敛为范围、指标、摘要、正文、辅助信息五级；日历在六周月份也固定容纳“三项目 + 更多”四行摘要。

当前剩余工作是完成真实交互验收、补齐必要提示，并继续收口项目规则和发布工程。

因此开发优先级固定为：

```text
数据安全 > 资料库生命周期 > 产品规则正确 > 桌面体验 > 发布包装
```

## 二、工程目标

第一可用版本应满足：

- 无需登录即可使用。
- 用户可以新建或选择本地 DayLog 资料库。
- 重启后自动恢复最近资料库和全部内容。
- 新增、修改、删除均安全写入 JSON。
- 每次变更同步维护受影响日期的 Markdown。
- 快速连续操作不会出现旧状态覆盖新状态。
- 保存失败可见、可重试、可恢复。
- 记录、明细、统计、项目和日历主链路闭环。

## 三、技术职责

```text
Tauri + Rust：资料库边界、文件事务、系统对话框、Finder、应用配置
React + TypeScript：页面、表单状态、视图计算、保存状态展示
Vite：开发与前端生产构建
本地资料库：用户数据本体
GitHub / Gitee：源码和安装包分发，不是运行时后端
```

文件系统写入不继续由任意 React 组件直接调用。前端通过窄化的 Tauri 命令请求“打开资料库、读取资料库、保存事务、在 Finder 中显示”，Rust 负责路径与磁盘安全。

## 五、资料库目标结构

```text
DayLog/
├── .daylog/
│   ├── events.json
│   ├── thoughts.json
│   ├── moods.json
│   ├── projects.json
│   ├── project-history.json
│   └── app-settings.json
└── days/
    └── YYYY/
        └── MM/
            └── YYYY-MM-DD.md
```

职责：

- JSON 是唯一程序数据源。
- Markdown 是从 JSON 生成的用户可读投影。
- 最近资料库路径和窗口状态保存在 macOS 应用配置目录，不写入资料库。
- 资料库内只保存需要随文件夹迁移的设置。

## 六、保存事务设计

### 6.1 基本约束

同一资料库在任意时刻只允许一个保存事务。

每次保存：

1. 前端形成完整的下一状态或明确的领域操作。
2. Rust 验证目标路径仍是有效资料库。
3. 前端校验必要字段、枚举、日期和项目引用。
4. 在内存中准备所有待写 JSON 和受影响 Markdown。
5. 写入同目录临时文件并刷新。
6. 替换正式文件。
7. 删除已无记录日期的 Markdown。
8. 返回成功或可理解的错误。

### 6.2 并发与顺序

- 所有保存进入单一队列。
- 后一次编辑不能被先发后至的旧写入覆盖。
- UI 编辑状态与持久化状态分开保存。
- 连续文本输入只在明确保存、失焦或防抖结束后提交。
- 更换资料库、关闭窗口前等待队列完成，或向用户提示。

### 6.3 失败处理

- 临时文件写入失败时不替换正式文件。
- 保存失败保留当前输入，并允许直接重试。
- 读取失败时不自动覆盖原文件。
- MVP 不实现事务日志、多版本备份和复杂自动恢复；真实使用中证明需要后再增加。

### 6.4 保存状态

统一状态机：

```text
idle → dirty → saving → saved
                    ↘ failed → saving
```

保存失败时保留当前输入，不清空表单。

## 七、实施阶段

### 阶段 0：工程收口

目标：建立可持续开发和验证的工程基线。

任务：

- 建立 Git 仓库或确认上级仓库边界。
- 添加 `.gitignore`，移除构建缓存和真实测试数据的版本跟踪风险。
- 把个人绝对路径和测试用户名称移出正式代码。
- 建立 `typecheck`、`test`、`build`、`tauri:check` 脚本。
- 定位 Vite 生产构建长期停在 `transforming` 的原因。

验收：

- 干净检出后可安装依赖、类型检查和构建。
- 发布资源不含真实用户数据。
- Rust 构建缓存不进入源码范围。

### 阶段 1：资料库生命周期

目标：应用启动使用真实资料库，而不是测试数据。

任务：

- 实现“新建资料库 / 打开已有资料库”首屏。
- 使用系统文件夹选择对话框。
- 初始化 `.daylog/` 和 `days/`。
- 实现六个 JSON 文件的读取、组合和校验。
- 在 macOS 应用配置目录记录最近资料库路径。
- 启动时自动恢复，失败时回到资料库选择页。
- 设置页接通更换资料库和 Finder。

验收：

- 新建资料库后生成合法空数据。
- 重新启动后恢复同一资料库。
- 选择从另一台设备复制来的资料库可恢复全部内容。
- 路径不存在、权限不足、JSON 损坏时不进入空白主界面。

### 阶段 2：安全持久化

目标：数据在快速操作、失败和重启下仍可靠。

任务：

- 将文件读写迁移到 Rust 资料库服务。
- 缩小 Tauri 权限，不再开放整个主目录递归写入。
- 实现串行保存、临时文件和替换。
- 根据操作计算受影响日期。
- 正确删除过期 Markdown。
- 增加保存状态、失败提示和重试。
- 移除前端 `console.error` 作为唯一失败处理的做法。

验收：

- 连续快速保存 10 次后重启，磁盘为最后一次状态。
- 临时文件写入失败时不覆盖正式文件。
- 修改事件日期后旧、新日期 Markdown 均正确。
- 删除某日最后一条记录后对应 Markdown 被删除。
- 两次同时保存不会产生混合版本 JSON。

### 阶段 3：统一数据契约与迁移

目标：代码、测试数据和文档只使用一套字段定义。

目标枚举：

```text
completion = excellent | progress | minimum | unplanned
ddlType = date | long-term | undecided
progress = active | completed | paused
lifecycle = normal | merged | deleted
```

任务：

- 为 `app-settings.json` 增加 `schemaVersion`。
- 移除资料库内部的绝对 `vaultPath`。
- 处理旧字段 `mood`、`specific-date`、`long-running`、`normal/active` 互换等历史数据。
- ID 改用可靠 UUID 或等价策略。
- 增加重复 ID、悬空项目引用和非法日期校验。

验收：

- 当前测试资料库可以无损迁移。
- 不支持的新版本资料库不会被旧应用覆盖。
- 迁移前保留备份，失败可回滚。

### 阶段 4：主链路规则修正

目标：现有页面符合产品基线。

记录：

- 标题或日期非法时不清空表单。
- 今日录入按本地时区计算。
- 保存成功和失败均有明确反馈。

明细：

- 单日感受、事件、时间摘要完整。
- 内在与外在区域使用一致的 40/60 分栏，纵向分界线对齐。
- 想法原位编辑使用明确的取消与保存；事件直接编辑并防抖保存，保存状态可见。
- 时间去向按项目汇总，圆环显示比例、图例只显示时间；左下默认列出当日全部事件且不自动选中。
- 删除有确认。
- 只有感受记录的日期也可进入。

项目：

- 过期 DDL 不进入进行中。
- 未命名项目永久置顶。
- 已有未命名项目时再次新增需确认。
- 文本编辑不逐字生成项目历史。
- 合并、删除后所有受影响日期同步更新。
- 修改项目状态后保留当前详情；切换项目分类时清空选择且不自动选择。

统计：

- 只承担区间复盘。
- 本周、本月以今天为默认锚点。
- 内部枚举不直接显示给用户。
- 时间分布按累计占比动态保留到首次达到或超过 80%，剩余项目合并为“其他”。
- 时间分布位于完成状态之前，并在圆环和图例中显示百分比。

视觉与内容配置：

- 记录页突出感受与想法，事实补充与自我觉察文案及视觉明确分离。
- 明细页按“一天的内在记录 / 一天的外在经历”组织。
- 提供石青、石绿、赭石、朱砂、绀青、紫棠、黄丹七套敦煌低饱和主题，设置页使用紧凑色点选择。
- 关照页文案、问候语、其他产品卡片、推荐文案、产品说明和版本信息集中在 `public/data/daylog-content.json`；100 件小事单独保存在 `public/data/energy-activities.json`。
- 将原“推荐”区域升级为“关照”：本地随机呈现原创 100 件关照小事，并为其他自我觉察产品保留可配置的飞书链接卡片；产品未配置时不显示占位入口。

日历：

- 综合事件、情绪和想法判断某日是否有记录。
- 点击进入明细页，而不是统计页。
- 日期格按投入展示前三个已命名项目，其他内容中性汇总为“更多”，五周和六周月份均不得裁切四行摘要。

### 阶段 5：桌面体验

任务：

- 关于页读取 Tauri 真实版本；后台检查远程 `daylog-content.json` 中的版本信息。无更新时只记录版本号与“已是最新版”，发现新版本后才显示飞书下载链接和设置提示点，不提供独立“检查更新”按钮。

- 选择原生标题栏或自定义标题栏，不能同时显示两套红黄绿按钮。
- 增加应用菜单和核心快捷键。
- 恢复窗口大小和位置。
- 增加“在 Finder 中显示”和可理解的文件错误提示。
- 完成键盘焦点、Tab 顺序、Escape 关闭弹窗和基础无障碍。
- 拆分重复 CSS，建立稳定的布局和组件层。

建议快捷键：

```text
⌘N  新增事实经历
⇧⌘N 新增感受体验
⌘S  保存当前编辑
⌘1...5 切换主要页面
⌘,  打开设置
```

### 阶段 6：测试与发布

测试层：

- 单元测试：校验、项目状态、日期、Markdown 转义和受影响日期计算。
- 集成测试：资料库初始化、加载、事务、恢复和迁移。
- UI 测试：记录、编辑、删除、项目合并、更换资料库。
- 手工桌面测试：安装、权限、Finder、关闭窗口和不同 macOS 版本。

发布任务：

- 完成正式图标和 bundle 元数据。
- 生成 `.app` 和 `.dmg`。
- 检查发布包不含测试数据、个人路径和调试权限。
- 内部试用版可暂不启用自动更新。
- 面向普通用户公开分发前完成 Developer ID 签名和 Apple notarization。

## 八、Markdown 实现要求

- 使用界面中文文案输出完成状态。
- 转义表格中的 `|`、换行和反斜杠。
- 想法与事件按稳定规则排序。
- 项目改名时更新所有引用该项目的日期。
- 空日期文件的删除必须属于同一保存事务。
- 不在每次变更时无差别重写全部历史 Markdown；只处理受影响日期。
- 提供“重新生成全部 Markdown”的维护操作，用于修复投影而不修改 JSON。

## 九、安全边界

- 只允许操作用户明确选择且验证通过的资料库。
- 所有拼接路径必须规范化并验证仍位于资料库内部。
- 不信任 JSON 文件内容，读取后必须校验。
- 不把资料库内容写入日志。
- 不把真实用户数据作为前端源码导入。
- 不使用 GitHub、Gitee 或任何云服务作为隐式运行时依赖。

## 十、非 MVP 范围

- 登录、账号和 Pro 权益。
- 云同步和多人协作。
- 在线支付。
- 附件管理。
- Markdown 双向编辑。
- 内置 AI 自动扫描整个资料库。
- Windows 发行；架构保持可移植，但首发平台为 macOS。
- 自动更新；公开发布准备阶段再评估。

## 十一、完成定义

一个阶段只有在以下条件同时满足时才算完成：

1. 功能按产品文档工作。
2. 有与风险相称的自动化测试。
3. 错误状态可见并可恢复。
4. 没有引入个人路径、真实测试数据或过宽权限。
5. 类型检查、Rust 检查和生产构建通过。
6. 在实际 Tauri 窗口完成手工验收。

在阶段 1、2 完成前，不将当前应用用于不可替代的真实记录。
