# DayLog Desktop 产品设计文档

> 最后更新：2026-08-12
> 版本：v0.2.0
> 适用范围：`daylog-desktop` macOS 本地桌面版
> 状态：产品基线，用于约束 MVP 功能、交互和数据语义

## 一、产品定义

DayLog Desktop 是一个安装在电脑里的本地时光日志本。

它帮助用户持续记录两类同等重要的内容：

```text
感受体验：我当时感觉如何、想到了什么
事实经历：我做了什么、投入多久、推进到什么程度
```

DayLog 不要求用户先建立完整计划，也不要求所有经历都有项目。它先让真实发生的事情被留下，再通过明细、项目、统计和日历帮助用户回看生活与工作的连续性。

一句话定位：

```text
DayLog 是一个本地优先、可长期保存、可以回看的个人时间日志。
```

它不是：

- 账号和会员系统。
- 云端管理后台。
- 强任务驱动的待办工具。
- 要求每一分钟都被量化的工时软件。
- 以项目管理取代个人感受的效率工具。

## 二、核心价值

### 2.1 记录真实发生

记录允许补录过去日期，也允许记录计划外经历。事实和感受不互相附属，用户可以只记录其中一种。

### 2.2 看见时间去向

项目、完成状态和投入时间用于帮助用户理解阶段变化，不用于绩效评判。

### 2.3 保持项目连续性

项目页回答的是“这件事是否仍在继续、已经投入了多少、最近发生了什么”，而不是建立复杂的任务层级。

### 2.4 数据真正属于用户

用户选择的 DayLog 资料库就是数据本体。JSON 支撑程序可靠运行，每日 Markdown 让数据可直接阅读、迁移、备份和交给其他工具处理。

## 三、产品原则

- 本地优先：MVP 无需登录，不依赖后端或在线数据库。
- 安全优先：保存失败必须可见，不能用界面上的成功掩盖磁盘写入失败。
- 记录与回看分开：记录页保持轻，历史编辑进入明细页。
- 感受与事实平等：两类记录在信息架构和视觉上保持同级。
- 项目服务于连续性：不把 DayLog 做成重型项目管理器。
- JSON 与 Markdown 双存储：JSON 是程序数据源，Markdown 是可读投影。
- 桌面原生：围绕窗口、键盘、文件夹和 Finder 设计，不复制网页首页。
- 可迁移：复制整个资料库并重新选择后，应恢复全部记录和资料库内设置。

## 四、目标用户与使用情境

主要用户是希望安静记录日常、项目推进、情绪和想法的个人用户。

典型使用情境：

1. 当天随手记录一段经历或一个想法。
2. 晚上回看当天发生的事情并修正记录。
3. 周末或月末查看时间分布和感受趋势。
4. 通过项目查看一件长期事情的投入与连续性。
5. 直接阅读 `days/` 中的 Markdown，或把它交给 AI 做阶段复盘。
6. 更换电脑时复制资料库，不依赖账号找回。

## 五、信息架构

### 5.1 功能区

桌面端主导航为：

```text
记录
明细
项目
统计
日历
```

页面职责必须互相区分：

| 页面 | 回答的问题 | 核心动作 |
|---|---|---|
| 记录 | 我现在要留下什么？ | 新增感受体验、事实经历 |
| 明细 | 某一天具体发生了什么？ | 单日回看、修改、删除、整理项目归属 |
| 统计 | 一段时间呈现什么趋势？ | 区间筛选、分布与趋势复盘 |
| 项目 | 一件持续的事情进展如何？ | 项目维护、合并、暂停、完成 |
| 日历 | 哪些日期留下了记录？ | 月度浏览、进入某日明细 |

`明细` 正式承接旧设计中的“统计页单日视图”。统计页不再同时承担单日编辑和区间分析，避免一个页面出现两套互斥结构。

### 5.2 产品区

侧边栏底部为：

```text
充能
设置
```

充能用于短时恢复、了解刘迷糊的其他自我觉察产品和传播 DayLog；设置只承载本地桌面版所需配置，不承载账号管理。

## 六、桌面端整体结构

```text
侧边栏：一级导航
顶部栏：居中的产品名称；仅在确有必要时显示短暂保存状态
中央区：当前页面主体
详情面板：选中内容的查看和编辑
```

桌面端应减少页面跳转和大弹窗。普通编辑尽量在页面或详情面板内完成；删除、合并、更换资料库等高风险操作使用确认弹窗。

应用顶部统一显示品牌名 `刘迷糊 DayLog · 见己`。功能页名称由侧边栏当前项表达，不再在顶部逐页重复，释放出的纵向空间归还给页面内容。

## 七、记录页

### 7.1 页面职责

记录页只负责新增，不显示历史记录列表。

页面同时提供两个职责不同的区域：

```text
感受与想法（主要区域，用于自我觉察）
事实经历（辅助区域，用于还原外部发生）
```

二者不能只靠标题区分。感受与想法拥有更大的书写空间和更柔和的视觉底色；事实经历使用结构化字段。事件备注只补充客观背景，不替代想法记录。

### 7.2 感受体验

字段：

- 归属日期。
- 情绪状态。
- 想法内容，可为空。

规则：

- 允许补录过去日期，也允许记录未来日期。
- 一天可以保存多条情绪和多条想法。
- 某日展示的“最后状态”取该归属日期最后保存的情绪。
- 一次保存至少产生一条情绪记录；想法非空时同时产生一条想法记录。
- 保存成功后清空想法，但保留日期和情绪，方便连续记录。

### 7.3 事实经历

字段：

- 归属日期。
- 时间段：清晨、上午、下午、晚上。新建和编辑事件都必须使用其中一项。
- 事件名称，必填。
- 项目归属，可为空。
- 投入分钟，必须为非负数。
- 完成状态。
- 备注，可为空。

完成状态的界面文案与内部值：

| 界面文案 | 内部值 | 语义 |
|---|---|---|
| 圆满完成 | `excellent` | 达到或超过当时预期 |
| 有所推进 | `progress` | 产生有效进展 |
| 保底完成 | `minimum` | 完成最低可接受部分 |
| 计划外 | `unplanned` | 未在原计划中但真实发生 |

标题为空、日期无效或分钟数无效时不清空表单，并在字段附近说明原因。

### 7.4 今日录入摘要

摘要按“录入动作发生的本地日期”统计，而不是按记录的归属日期统计。

示例：

```text
今日录入：最后状态 有点愉快 · 想法 2 条 · 事实经历 5 条 · 累计投入 3小时20分钟
```

今天补录过去日期的内容仍计入今天的录入摘要。时间计算以设备本地时区为准，不能直接使用 UTC 日期截断。

## 八、明细页

### 8.1 页面职责

明细页负责单日回看与整理，是记录页之后的主要校正入口。

### 8.2 页面内容

- 日期切换。
- 当日最后情绪。
- 当日想法列表。
- 当日时间分布和完成状态摘要。
- 事件详情与编辑面板。

页面只采用“一天的内在记录 / 一天的外在经历”两个语义区域，两区均使用一致的 `40% / 60%` 左右分栏并严格对齐。情绪与想法组成较高的内在区域；外在区域左上按项目呈现时间去向、左下默认列出当日全部事件，右侧显示所选事件详情。点击项目后筛选左下事件，再次点击恢复全部事件；筛选项目时不自动选中事件。

左右分栏依靠内容、留白和轻微底色区分，不使用明显的纵向分割线。

### 8.3 编辑规则

- 想法点击正文或修改按钮后原位进入紧凑编辑框，使用明确的“取消 / 保存”，不因失焦自动提交；事件详情直接编辑，停止输入约 800 毫秒后自动保存，并显示“有未保存修改 / 保存中 / 已保存 / 保存失败”。
- 不允许每次键盘输入都直接触发整库写入和历史记录。
- 删除想法或事件前需确认；确认内容说明会同步更新对应日期 Markdown。
- 修改事件日期时，旧日期和新日期的 Markdown 都必须同步处理。
- 修改项目归属后，项目累计时间、记录天数和统计结果立即重算。

### 8.4 日期来源

从日历点击日期时进入明细页并选中该日。某天只有情绪或想法、没有事实经历时，也必须可以进入明细页。

## 九、统计页

### 9.1 页面职责

统计页只负责区间复盘，不负责逐条历史编辑。

日期范围：

```text
本周 / 本月 / 自定义 / 全部
```

“本周”和“本月”默认以今天为基准；如果用户从某个历史日期进入统计，可明确显示当前统计锚点，避免把“最新一条数据所在周”误称为本周。

### 9.2 页面内容

1. 记录天数、想法条数、事实经历条数、累计投入。
2. 情绪趋势：每天取最后一条情绪。
3. 想法数量与记录天数。
4. 项目时间分布。项目按投入从高到低累计，直到累计占比首次达到或超过 80% 的项目均独立展示；剩余项目合并为中性色“其他”。因此边界不要求精确等于 80%。
5. 完成状态分布。
6. 阶段复盘；内容过多时展示前三项目、暂不设置项目和其他。

统计只基于当前内存中已成功加载的数据。保存失败的数据不得被长期当作已落盘数据展示。

## 十、项目页

### 10.1 页面职责

项目页管理“持续发生的事情”，不管理任务清单，也不作为事实经历的主要整理入口。

### 10.2 三类状态

项目有三个维度，不能混用：

```text
DDL 类型：date | long-term | undecided
进度标签：active | completed | paused
生命周期：normal | merged | deleted
```

自然展示状态由三个维度共同推导：

- 进行中：`lifecycle=normal`、`progress=active`，且为长期推进，或指定日期未过期。
- 待计划：`lifecycle=normal`、`progress=active`，且 DDL 为还没想好。
- 已过期：指定日期已过期且仍为 `active`；仅在全部项目中查看，不冒充进行中。
- 已完成：`progress=completed`。
- 已暂停：`progress=paused`。
- 已合并、已删除：不进入普通项目列表。

主筛选为“进行中 / 待计划 / 全部”。完成、暂停和过期可作为全部项目中的次级筛选，不能改变其数据语义。

切换主筛选时必须清空当前项目选择，右侧回到“选择一个项目查看详情”，不能自动选择新分类中的第一项。仅修改当前项目状态时继续保留其详情，直到用户主动选择其他项目或切换主筛选。

### 10.3 未命名项目

新建项目先产生一个“未命名项目”并打开右侧详情。

- 所有未命名且未设置 DDL 的项目始终排在列表最前，不受 24 小时限制。
- 再次新增前，如已有未命名项目，提示：`还有未命名项目未处理，仍要继续新增吗？`
- 项目名称不能保存为空字符串。

### 10.4 项目详情

- 项目名称。
- DDL 类型和日期。
- 累计投入。
- 记录天数，即存在关联事实经历的不同日期数。
- 完成、暂停进度标签。
- 关联事实经历数量和最近记录。
- 合并与删除。

普通字段在详情面板内编辑。文本编辑应在失焦、按下保存或防抖结束后形成一次更新，而不是每个字符形成一次项目历史。

### 10.5 合并

合并目标可以是任意生命周期正常的其他项目，包括进行中、待计划、完成、暂停和过期项目。

合并后：

- 来源项目 `lifecycle` 变为 `merged`，记录 `mergedIntoId`。
- 来源项目的全部事实经历改归目标项目。
- 受影响日期的 Markdown 重新生成。
- 项目历史记录来源、目标和发生时间。
- 来源项目不再进入普通项目列表。

### 10.6 删除

无关联事实经历时，确认后软删除。

有关联事实经历时必须选择：

```text
暂不设置项目
合并到其他项目
取消
```

删除是生命周期变化，不立即物理移除项目数据，以便恢复和追踪历史。

## 十一、日历页

日历页是只读的月度索引。

每个日期格固定保留四行摘要容量：按投入时间展示前三个已命名项目，剩余已命名项目与未分类投入合并为不使用项目色的“更多”。即使一个月跨六周，也不能裁掉第四行。

每个日期显示：

- 是否有任意类型记录。
- 事实经历数量与累计投入。
- 主要项目摘要。
- 只有感受记录时也要有轻量标记。

点击有记录的日期进入明细页。日历不直接承担编辑、项目管理或复杂筛选。

## 十二、充能与设置

### 12.1 充能

充能页是核心记录流程之外的轻量入口，三组内容全部铺开并按以下顺序组织：

1. `此刻充能`：从 100 件原创充能小事中随机呈现一件可立即开始的行动。
2. `继续探索自己`：以外部飞书链接承接自我探索工具、团体探索、1v1 深度对话、冥想音频等产品，不在 DayLog 内复制完整产品。
3. `分享 DayLog`：提供自然、可直接复制给朋友的推荐文案。

随机充能不采用强调输赢或刺激感的转盘，而使用安静的行动卡。每次只显示一件事及其分类、预计时间和简短做法；切换仅做一次本地随机计算，不写入资料库，也不影响主页面加载。

100 件小事由身体舒展、感官苏醒、情绪安顿、秩序恢复、自然连接、关系滋养、创造表达、微小探索、安静休息和温柔回看十类组成。分类只用于内容平衡，不要求用户先筛选。

充能页文案、记录页问候语、其他产品卡片、推荐文案、产品说明链接和版本信息集中保存在 `public/data/daylog-content.json`；100 件充能小事集中保存在 `public/data/energy-activities.json`。两者均可直接修改，不需要改动页面组件。`products` 为空时不显示虚假的产品入口。

新增其他产品时只需在 `products` 数组加入：

```json
{
  "title": "产品名称",
  "description": "一句话说明它能带来的帮助",
  "label": "去了解",
  "url": "https://飞书链接"
}
```

### 12.2 设置

设置页包含：

- 当前资料库名称与路径。
- 更换资料库。
- 在 Finder 中打开。
- 外观主题。提供石青、石绿、赭石、朱砂、绀青、紫棠和黄丹七套敦煌壁画色系的低饱和配色，只显示色点，不向用户解释内部设计语义。
- 当前产品版本、更新状态和产品说明入口。版本检查在后台进行，不提供“版本更新”操作按钮；只有发现新版本时才显示飞书下载链接。设置页不重复展示隐私说明。

更换资料库是高风险操作：如果存在未完成保存，必须先完成或明确提示；新资料库加载成功前不能丢弃当前内存数据。

MVP 不显示不可用的“检查更新”入口。自动更新进入公开发布阶段后再启用。

### 12.3 版本提醒与下载

当前阶段采用“轻量版本提醒 + 飞书手动下载”，不在应用内自动替换程序：

- 当前版本从 Tauri 应用配置读取，不在页面组件中写死。
- `public/data/daylog-content.json` 中的 `links.updateDownloadUrl` 固定指向飞书版本下载页，用户直接在飞书下载客户端，不跳转到其他下载平台。
- 同一文件中的 `remoteContentUrl` 是旧客户端能够读取的远程 JSON 地址；未配置时不伪装已检查，只显示当前版本并提供飞书下载入口。
- 配置远程地址后，应用启动时每天最多后台拉取一次。应用只读取产品运营内容和版本号，不上传资料库内容或使用行为。
- 有新版本时在设置入口显示克制的小圆点，并在关于区域显示新版本号、更新摘要和飞书下载链接；没有新版本时不显示下载入口。
- 远程读取失败时优先使用上次缓存，没有缓存则回退安装包内置内容，不阻塞记录功能。

发布时先把安装包上传到固定飞书下载页，再更新远程 `daylog-content.json` 的 `release`。仅修改新安装包内部文件无法提醒已经安装旧版本的用户；详细步骤见 `docs/DayLog 内容维护说明.md`。

## 十三、本地资料库

### 13.1 结构

```text
DayLog/
├── .daylog/
│   ├── events.json
│   ├── thoughts.json
│   ├── moods.json
│   ├── projects.json
│   ├── project-history.json
│   └── app-settings.json
└── days/
    └── YYYY/
        └── MM/
            └── YYYY-MM-DD.md
```

### 13.2 数据职责

- `.daylog/*.json`：程序真实数据源，不建议用户手动编辑。
- `days/*.md`：由 JSON 自动生成的可读投影，可以复制、阅读和交给其他工具。
- Markdown 不能反向覆盖 JSON；未来若支持导入，必须作为独立迁移流程。

### 13.3 首次启动

1. 选择“新建资料库”或“打开已有资料库”。
2. 新建时选择空文件夹并初始化 `.daylog/` 与 `days/`。
3. 打开已有资料库时先检查结构、版本和数据合法性。
4. 加载成功后进入记录页。
5. 设备本地配置记住最近资料库路径。

应用不能把开发者电脑的绝对路径作为正式默认路径。

### 13.4 设置归属

需要随资料库迁移的设置保存在 `.daylog/app-settings.json`，例如主题和项目配色。

只属于当前设备的状态保存在系统应用配置目录，例如：

- 最近打开的资料库路径。
- 最近资料库列表。
- 窗口大小和位置。

资料库内部不保存依赖当前设备的绝对 `vaultPath`。

## 十五、Markdown 规则

每日文件路径：

```text
days/YYYY/MM/YYYY-MM-DD.md
```

结构：

```md
# 2026-07-31 · DayLog

## 感受体验

### 情绪状态
有点愉快

### 想法
- 22:00 今天终于把桌面端逻辑理顺了。

## 事实经历

| 时间 | 事件 | 项目 | 投入 | 完成 | 备注 |
|---|---|---|---:|---|---|
| 上午 | 整理桌面端结构 | DayLog 桌面版 | 80m | 有所推进 | 确定页面职责 |

## 当日投入

- DayLog 桌面版：1小时20分钟
```

生成规则：

- 新增记录：生成或更新归属日期 Markdown。
- 修改内容：更新该记录当前归属日期 Markdown。
- 修改日期：同时更新旧日期和新日期。
- 删除某日最后一条记录：删除该日 Markdown，不能保留过期内容。
- 项目改名、合并或删除：重新生成所有受影响日期。
- 表格中的 `|`、换行和反斜杠必须正确转义。
- 完成状态输出中文文案，不输出内部枚举。
- 写入失败时保留上一份完整 Markdown。

## 十六、保存与错误体验

顶部栏或当前编辑区域显示统一保存状态：

```text
未修改 / 保存中 / 已保存到本地 / 保存失败
```

规则：

- 同一资料库的保存严格串行。
- 数据校验通过后才开始接触磁盘。
- 先准备全部目标内容，再通过临时文件和替换写入。
- 任一步失败都不能破坏上一份正式文件。
- 保存失败必须提供重试和打开资料库位置的入口。
- 退出、更换资料库或关闭窗口前，如有未完成保存，必须等待或提示。
- 保存成功提示只短暂出现，平时不占据顶部栏；保存失败状态持续保留。

## 十七、迁移、隐私与边界

换设备：复制整个 DayLog 文件夹，在新设备选择已有资料库即可。

隐私承诺：

- MVP 不上传记录、资料库路径或使用行为。
- 不要求账号。
- 文件系统权限只覆盖用户明确选择的资料库，不申请整个主目录的递归读写。
- 测试数据和开发者个人路径不得进入发布包。

MVP 不包含：

- 云同步和多人协作。
- 邮箱登录、Pro 权益和支付。
- 附件管理。
- Markdown 双向编辑。
- 内置 AI 读取全部资料库。
- 自动更新、签名和公证；这些属于公开发布准备。

## 十八、MVP 验收标准

只有同时满足以下条件，才能把当前版本称为可长期试用的桌面 MVP：

1. 新建、选择、重新打开资料库完整可用。
2. 应用启动读取真实资料库，不加载测试数据。
3. 新增、修改、删除在重启后不丢失。
4. JSON 与 Markdown 始终一致，删除最后一条记录不会残留旧文件。
5. 连续快速编辑不会发生旧数据覆盖新数据。
6. 保存失败对用户可见，正式文件可恢复。
7. 项目状态、合并和删除符合本文件定义。
8. 日历能进入只有感受记录的日期。
9. 发布包不含个人绝对路径和测试用户数据。
10. macOS `.app` 可在目标系统稳定启动并完成主链路。
